# Развёртывание Django-приложения

## 1. Назначение

Документ описывает локальное развёртывание системы
бронирования оборудования и порядок публикации
приложения на платформе Render.
В качестве основы используется технология
развёртывания, рассмотренная в ПЗ №8.

## 2. Архитектура

В облачной среде используются следующие компоненты:
- Render Web Service — размещение приложения.
- Gunicorn — WSGI-сервер.
- Django — серверная логика.
- Django REST Framework — REST API.
- PostgreSQL — постоянное хранение данных.
- WhiteNoise — обслуживание статических файлов.
- GitHub — хранение исходного кода.

Браузер взаимодействует с приложением через HTTPS.

## 3. Подготовка зависимостей

Для облачного развёртывания требуются:
- Django;
- djangorestframework;
- gunicorn;
- whitenoise;
- dj-database-url;
- psycopg;
- python-dotenv.

Все зависимости должны быть перечислены
в requirements.txt с проверенными версиями.

## 4. Переменные окружения

Для конфигурации используются:

DJANGO_SECRET_KEY — секретный ключ Django.

DJANGO_DEBUG — режим отладки, в облаке False.

DJANGO_ALLOWED_HOSTS — разрешённые домены.

DJANGO_CSRF_TRUSTED_ORIGINS — доверенные
HTTPS-источники.

DATABASE_URL — адрес подключения к PostgreSQL.

Реальные секретные значения не публикуются
в репозитории и документации.

## 5. Локальное развёртывание

Создать виртуальное окружение:

    py -3.13 -m venv .venv

Активировать окружение:

    .\.venv\Scripts\Activate.ps1

Установить зависимости:

    python -m pip install -r requirements.txt

Создать .env по образцу .env.example
и задать собственный секретный ключ.

Выполнить миграции:

    python manage.py migrate

Проверить конфигурацию:

    python manage.py check

Запустить сервер:

    python manage.py runserver

## 6. Подготовка к облачному развёртыванию

Перед публикацией необходимо:
1. Установить Gunicorn и WhiteNoise.
2. Настроить чтение DATABASE_URL.
3. Настроить обслуживание статики.
4. Проверить работу при DEBUG=False.
5. Подготовить сценарий build.sh.
6. Отправить исходный код в GitHub.

Эти настройки проверяются отдельно
перед публикацией проекта.

## 7. Публикация на Render

### Создание PostgreSQL

В Render выбрать New -> Postgres.
Создать базу данных и дождаться статуса Available.
Для подключения Web Service к PostgreSQL,
расположенной в том же регионе Render,
используется Internal Database URL.
Фактическое значение URL является секретом.

### Создание Web Service

В Render выбрать New -> Web Service.
Подключить GitHub-репозиторий проекта.
Основные параметры:

Language: Python

Branch: main

Root Directory: пустое, если manage.py
находится в корне репозитория.

Build Command:

    bash build.sh

Start Command:

    gunicorn config.wsgi:application --bind 0.0.0.0:$PORT

Web Service и PostgreSQL должны располагаться
в совместимом регионе.
Необходимо использовать бесплатный тариф,
если он доступен.

### Переменные окружения

В настройках Web Service указать:
- DATABASE_URL
- DJANGO_SECRET_KEY
- DJANGO_DEBUG=False
- DJANGO_ALLOWED_HOSTS
- DJANGO_CSRF_TRUSTED_ORIGINS

В DATABASE_URL передаётся внутренний адрес
подключения PostgreSQL.
Нельзя публиковать пароль базы данных,
секретный ключ или полный DATABASE_URL.

## 8. Сборка приложения

Сценарий build.sh должен устанавливать
зависимости и собирать статические файлы.

Команды:

    python -m pip install -r requirements.txt

    python manage.py collectstatic --noinput

Сборка и запуск сервера выполняются отдельно.

## 9. Миграции PostgreSQL

После настройки DATABASE_URL необходимо
выполнить миграции из контролируемого
окружения, подключённого к облачной базе:

    python manage.py migrate

Проверить результат:

    python manage.py showmigrations

Команды должны работать именно с PostgreSQL,
а не с локальной SQLite.
Локальная и облачная базы независимы.
Данные не переносятся автоматически.

## 10. Проверка облачной версии

После фактической публикации необходимо проверить:
- открытие интерфейса по HTTPS;
- загрузку CSS и JavaScript;
- авторизацию;
- GET /api/equipment/;
- GET /api/reservations/;
- создание бронирования;
- подтверждение бронирования;
- сохранение данных после перезапуска Web Service.

Результаты необходимо зафиксировать
скриншотами и HTTP-статусами.

## 11. Локальная проверка воспроизводимости

Для СРС №8 создана отдельная копия проекта
spo_srs8.

Проверка показала:
- зависимости установлены успешно;
- миграции создали новую базу SQLite;
- Django check завершился без ошибок;
- все 10 автоматических тестов пройдены;
- пользовательский интерфейс работает;
- GET-запросы возвращают HTTP 200;
- бронирование создаётся и подтверждается;
- данные сохраняются после перезапуска.

Проверка облачного развёртывания
документируется отдельно от локальной.

## 12. Заключение

Инструкция описывает подготовку окружения,
конфигурацию, миграции, сборку и запуск
веб-приложения.
Разделение локального и облачного запуска
позволяет проверять их независимо и
избегать смешения SQLite и PostgreSQL.
